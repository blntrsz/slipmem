# @slipmem/web

The Foldkit single-process UI for slipmem. It renders the Markdown note
repository through the JSON API from `@slipmem/server`; there is no separate API
process and no browser-only source of truth.

Every page load and mutation reads or writes the same `.slipmem/` files as the
CLI and MCP surfaces. The disposable search index is refreshed before search and
topic reads.

## Running

From the repository root:

```sh
slipmem init          # or: bun run slipmem -- init
bun run web
```

`bun run web` starts the Vite development host with server-side rendering. The
note root follows `SLIPMEM_DIR`, then the nearest ancestor `.slipmem/`. A
missing root stops startup with the `slipmem init` guidance.

The scripts use `bun --bun vite` because the Markdown index uses `bun:sqlite`.
Vite's development SSR runner must execute under Bun.

## Pages

| Route | Purpose |
| --- | --- |
| `/` | Bounded note list; `type` and `topic` query filters |
| `/notes/:id` | Note detail with ID, file path, topics, and full text |
| `/new?type=...` | Create a fleeting, literature, or permanent note |
| `/notes/:id/edit` | Edit title, content, reference, and topics |
| `/notes/:id/delete` | Explicit delete confirmation before the backup move |
| `/search?q=...` | Ranked, bounded search with IDs, paths, and excerpts |
| `/topics` | Topic inventory; all-type count with per-type breakdown and fleeting opt-in |
| `/wiki/:topic` | On-demand cited topic page; `mode=extractive\|synthesized`, `includeFleeting=true` |
| `/review` | Pending agent proposals with an inspectable line diff |
| `/health` | Refreshed index count, wiki synthesis capability, and local security posture |

Note text is always rendered through Foldkit text nodes as data, never trusted
HTML. Topic pages show derived structured sections and the Markdown rendering,
with source IDs and paths. Nothing generated by a topic page is persisted as a
second source of truth.

The topics index counts every note type. Permanent and literature notes are
cited by default, so the page shows a per-type breakdown and offers an
`includeFleeting=true` link; the topic page explains the citation scope and
links to every note carrying the topic when a page is empty.

Extractive topic pages are always available. The "Try synthesized" action is
rendered only when `/api/health` and the wiki response report a configured
synthesizer. A failed synthesized request keeps an explicit "Use extractive
page" link, so the UI never strands the reader on a 501.

The Health page refreshes the disposable index before showing its count, so an
external CLI write is reflected immediately rather than at the next search.
Approval is a local policy gate, not authentication or an OS sandbox; see the
network posture below.

## Review flow

An agent using MCP creates a pending proposal for permanent writes,
reclassification, or any delete. `/review` lists the proposal summary, actor,
expiry, target ID, path, staleness, and a line diff. Approve applies the
proposal; reject removes it without touching notes. A stale or expired proposal
cannot be approved. There is no approve action in the web API that MCP can call.

## Production

```sh
bun run web:build
PORT=3000 bun run web:serve
```

The build writes the client bundle to `dist/client`, the Web `fetch` handler to
`dist/server/fetch.js`, and `dist/server/foldkit.build.json`. `web:serve` runs
that handler with `Bun.serve` and serves built client assets. `PORT` and `HOST`
select the listening address; they default to `3000` and `127.0.0.1`.

The API and MCP endpoint have no authentication and note files are plaintext, so
the server binds to loopback by default. Setting `HOST` to a non-loopback value
prints an explicit warning; only do it when you can restrict access at the
network level.

Pending agent writes require approval at `/review`. That gate is a local policy
for this UI, not authentication and not an OS sandbox: another local process
that can reach the port can bypass it and edit the Markdown files directly.

Synthesized wiki pages need an explicitly configured local agent or registered
model adapter. The default is extractive, which is always available. A
configured agent normally runs through a probed OS sandbox; the documented
`SLIPMEM_WIKI_AGENT_UNSAFE=1` override is explicitly unsafe and grants the
agent the slipmem user's full filesystem privileges.

## JSON API

The canonical API is documented in
[`packages/server/README.md`](../server/README.md). Quick examples:

```sh
curl http://localhost:3000/api/notes
curl -X POST http://localhost:3000/api/notes \
  -H 'content-type: application/json' \
  -d '{"type":"fleeting","title":"A thought","content":"Capture it"}'
curl 'http://localhost:3000/api/search?q=recall&limit=5'
curl http://localhost:3000/api/wiki/agent-memory
curl http://localhost:3000/api/pending
```

The old `/api/notes/:type` routes remain as compatibility adapters for one
release; the UI uses ID-based routes.
